# Обновление

```sh
curl -fsSL https://raw.githubusercontent.com/orgflycms/release/main/install.sh | sudo sh
```

Вошли как root, а `sudo` на сервере нет — уберите `sudo` из команды:
`… | sh`. Запускайте обновление в `tmux` или `screen`, чтобы потеря SSH не оборвала
сеанс. Сам установщик игнорирует HUP во время обновления; во время
обработки ошибки также игнорирует INT и TERM, чтобы возврат бинарника
не прервался на полпути.

Та же команда, что и при установке. Скрипт определяет один тег релиза,
скачивает движок и `SHA256SUMS`, проверяет сумму и версию до замены
бинарника. Затем спрашивает скачанный бинарник, подходит ли ему Postgres
магазина: если новой версии нужен сервер базы новее, обновление
останавливается, ничего не изменив, — раздел
[«Обновление Postgres»](#обновление-postgres). Если подходит, скрипт об
этом молчит. Нет файла сумм или сумма не совпала — обновление прекращается,
прежний бинарник и работающая служба остаются на месте.

Перед заменой скрипт останавливает магазин, сохраняет базу и прежний
бинарник, затем устанавливает новую версию и запускает службу. Во время
копирования и запуска магазин недоступен. Если `pg_dump` или сжатие
завершились ошибкой, замены не будет, скрипт попытается снова запустить
прежнюю службу. Данные, картинки и плагины сохраняются. Миграции
догоняют схему при старте.

## Обновление Postgres

Новая установка требует Postgres 18. Уже работающий магазин обновляется на
том Postgres, на котором стоит, пока новой версии магазина или плагину не
понадобится сервер новее:

- **новая версия магазина.** Перед обновлением установщик спрашивает
  скачанный бинарник (`flycms -license`, строки `postgres`,
  `postgres_required` и `postgres_conflict`) — до остановки службы. При
  конфликте обновление останавливается с ошибкой «найден Postgres N, а
  версии vX.Y.Z нужен M или новее», магазин продолжает работать на прежней
  версии. Нет конфликта — нет ни остановки, ни предупреждения;
- **плагин.** Автор может указать в `plugin.json` минимальную версию
  Postgres. Плагин с требованием выше установленного сервера из
  маркетплейса не ставится (прежняя версия плагина остаётся), а положенный
  в папку руками — не загружается: причина видна на странице «Плагины».

В обоих случаях обновите Postgres и повторите действие.

### Одной командой

Для стандартной установки — локальный Postgres из пакетов Debian или
Ubuntu, `FLYCMS_DSN` по умолчанию:

```sh
curl -fsSL https://raw.githubusercontent.com/orgflycms/release/main/postgres-upgrade.sh | sudo sh
```

Запускайте в `tmux` или `screen`. Скрипт:

1. находит кластер магазина на порту 5432 и проверяет, что места на диске
   хватит на второй такой же; если Postgres уже 18 или новее — сообщает об
   этом и выходит;
2. ставит пакет `postgresql-18` (при необходимости подключает репозиторий
   PGDG) — магазин в это время ещё работает;
3. останавливает магазин и переносит кластер: `pg_upgradecluster -v 18 N
   main`. Новый кластер занимает порт 5432, прежний остаётся на диске —
   остановленный, на другом порту, в ручном запуске;
4. проверяет: новый кластер запущен на 5432, магазин входит в базу, число
   строк в таблицах магазина то же, что до переноса, служба магазина
   запустилась и слушает свой порт.

Магазин недоступен на шагах 3 и 4: это время дампа и восстановления базы.

**Если что-то пошло не так** — `pg_upgradecluster` завершился ошибкой,
проверка не сошлась или магазин не запустился на новом сервере, — скрипт
удаляет недособранный новый кластер, возвращает прежнему порт 5432 и
автозапуск и запускает магазин на нём. Данные прежнего кластера перенос не
меняет. Журнал переноса — в папке `/var/tmp/flycms-postgres-XXXX`, её
путь скрипт печатает.

После успешного переноса проверьте витрину, вход владельца и заказы, затем
удалите прежний кластер — команду скрипт напечатает:

```sh
pg_dropcluster 15 main
```

Затем, если обновление магазина останавливалось на версии Postgres,
повторите его.

Свою базу — другой сервер, порт или роль в `FLYCMS_DSN`, управляемую базу —
скрипт не трогает: обновляйте её средствами её хозяина.

### Вручную

То же по шагам — если нужен другой порядок или целевая версия. Порядок для
локального Postgres на Debian и Ubuntu, поставленного из пакетов
(`pg_lsclusters` показывает его кластеры). Команды выполняются от root.

1. Остановите магазин и сохраните копию всего сервера базы:

   ```sh
   systemctl stop flycms
   umask 077
   saved=$(mktemp -d /var/tmp/flycms-pgupgrade-XXXX)
   su postgres -c pg_dumpall | gzip >"$saved/all.sql.gz"
   gzip -t "$saved/all.sql.gz"
   ```

2. Подключите репозиторий PGDG, если Postgres 18 в системе ещё не доступен
   (`apt-cache policy postgresql-18` не показывает кандидата):

   ```sh
   apt install -y postgresql-common ca-certificates
   /usr/share/postgresql-common/pgdg/apt.postgresql.org.sh
   ```

   Скрипт покажет, какой репозиторий подключит, и попросит нажать Enter.

3. Поставьте Postgres 18 и посмотрите кластеры. В первой колонке — версия
   действующего кластера, дальше она обозначена `15`; подставьте свою:

   ```sh
   apt install -y postgresql-18
   pg_lsclusters
   ```

4. Посмотрите вывод `pg_lsclusters`. Если кроме вашего кластера в нём
   появился `18 main`, это пустой кластер, созданный при установке пакета
   (так делают старые версии `postgresql-common`; новые его не создают,
   когда на сервере уже есть кластер). Он мешает переносу —
   `pg_upgradecluster` остановится с ошибкой `target cluster 18/main
   already exists`. Удалите его; если строки `18 main` нет, эту команду
   пропустите:

   ```sh
   pg_dropcluster --stop 18 main
   ```

   Перенесите в 18 свой кластер:

   ```sh
   pg_upgradecluster -v 18 15 main
   ```

   `pg_upgradecluster` переносит данные через `pg_dump`, новый кластер
   занимает прежний порт, а старый переводится на свободный порт и в ручной
   запуск. Старый кластер при этом не удаляется.

5. Проверьте версию и запустите магазин:

   ```sh
   pg_lsclusters
   su postgres -c "psql -Atc 'SHOW server_version'"
   systemctl start flycms
   ```

   Затем, если обновление магазина останавливалось, повторите его.

6. Когда убедитесь, что магазин работает, удалите старый кластер:

   ```sh
   pg_dropcluster 15 main
   ```

Подробности — `man pg_upgradecluster` и раздел «Upgrading» в
`/usr/share/doc/postgresql-common/README.Debian.gz`. Если
`pg_upgradecluster` завершился ошибкой, прежний кластер остаётся на месте,
а недособранный новый удаляется. Проверьте по `pg_lsclusters`, что прежний
кластер запущен (`online`), иначе запустите его — `pg_ctlcluster 15 main
start`, — затем запустите магазин и разберитесь с ошибкой до повторной
попытки.

## Лицензия и новая версия

Лицензия включает год обновлений. Версия, вышедшая после этого срока, ключ
не примет: магазин будет работать как бесплатный — товары останутся на
месте, но новые сверх 200 добавить будет нельзя, пока лицензия не продлена.

Перед обновлением скрипт спрашивает об этом скачанный бинарник новой версии
(`flycms -license`) — до любых изменений. Если новая версия выходит за срок
обновлений вашей лицензии, появится предупреждение с датами и ссылкой на
продление, затем скрипт ждёт 30 секунд; прервать обновление можно `Ctrl+C`
— магазин останется на прежней версии. Обновление не запрещается: без
терминала отсчёт такой же, вопросов скрипт не задаёт. Проверить заранее:

```sh
systemd-run --wait --pipe --collect --quiet --uid=flycms --gid=flycms \
  --property=WorkingDirectory=/opt/flycms \
  --property=EnvironmentFile=/etc/flycms.env \
  /usr/local/bin/flycms -license
```

Команда выполняется от root. Файл окружения читает systemd: через `.` или
`source` его подключать нельзя — `&` в строке подключения к базе оболочка
примет за команду, и статус покажет «база недоступна».

Команда печатает статус лицензии установленной версии: `status: valid` —
ключ действует, `outdated` — версия вышла после срока обновлений,
`wrong_domain` — ключ выпущен для другого домена или магазин ещё не
открывали по адресу домена лицензии.

## Unit-файл службы

Вместе с бинарником скрипт берёт `flycms.service` из того же тега релиза.
Если установленный `/etc/systemd/system/flycms.service` с ним совпадает,
ничего не происходит. Если отличается — в начале обновления, до любых
изменений, появится предупреждение: файл будет заменён, прежний сохранится
рядом как `flycms.service.prev-<дата и время>`. Затем скрипт ждёт
15 секунд; прервать обновление можно `Ctrl+C`. Без терминала отсчёт такой
же, вопросов скрипт не задаёт.

Свои настройки службы держите в
`/etc/systemd/system/flycms.service.d/*.conf` (`systemctl edit flycms`):
этот каталог установщик не трогает, и замена unit-файла их не затронет.
Подробнее — [install.md](install.md#свои-настройки-службы).

Unit не останавливает обновление: если файл не скачался или прежний не
удалось сохранить, остаётся прежний unit и скрипт предупреждает об этом.
Если новая версия не запустилась и скрипт возвращает прежний бинарник, он
возвращает и прежний unit. Сохранённые копии `flycms.service.prev-*`
скрипт не удаляет — лишние уберите сами.

В `/etc/flycms.env` дописываются только отсутствующие настройки. Домен,
DSN, код установки и заданные значения, включая пустой адрес https,
сохраняются. Сертификаты новых установок — в `/opt/flycms/certs`,
переход со старых путей описан в [install.md](install.md#домен-и-https).

Версия сейчас:

```sh
flycms -version
```

## Конкретная версия

```sh
curl -fsSL https://raw.githubusercontent.com/orgflycms/release/main/install.sh | sudo FLYCMS_VERSION=v0.2.0 sh
```

Тег должен содержать бинарник, `SHA256SUMS` и `flycms.service` в дереве
репозитория по этому тегу: без unit-файла первая установка остановится, а
обновление оставит прежний unit. Unit старого тега заменит установленный
так же, как при обычном обновлении. Старые релизы без
контрольных сумм установщик не принимает. Список — в
[релизах](https://github.com/orgflycms/release/releases).

**Выбор старого тега сам по себе не откатывает схему базы.** Старый движок
может не работать после новых миграций. Для возврата к состоянию до
обновления нужны прежний бинарник и соответствующий дамп базы.

## С v0.1.0 — через v0.2.0

Версии новее `v0.2.0` обновляют магазины начиная с `v0.2.0`. Магазин на
`v0.1.0` обновляется в два шага: сначала до `v0.2.0`, затем — до последней
версии.

```sh
curl -fsSL https://raw.githubusercontent.com/orgflycms/release/main/install.sh | sudo FLYCMS_VERSION=v0.2.0 sh
curl -fsSL https://raw.githubusercontent.com/orgflycms/release/main/install.sh | sudo sh
```

Вторую команду запускайте, когда магазин заработал на `v0.2.0`. Если
запустить обычное обновление сразу, установщик остановится до скачивания и
покажет эти же две команды: магазин продолжит работать на `v0.1.0`, ничего
не изменится. Магазины на `v0.2.0` и новее обновляются одной командой, как
раньше.

## Копии перед обновлением

В `/opt/flycms/backup/` создаётся пара с датой UTC и версией прежнего
бинарника, например:

```text
20261113T120000Z-v0.1.0.sql.gz            дамп SQL, 0600
20261113T120000Z-v0.1.0.flycms            прежний бинарник, 0600
20261113T120000Z-v0.1.0.installer-backup  метка завершённой копии, 0600
```

Папка принадлежит root с правами 0700. Перед остановкой проверяется
свободное место по размеру базы. Дамп снимается от пользователя службы с
DSN из `/etc/flycms.env`, включая пароль, другую роль или TCP. `pg_dump`
сам сжимает SQL через `-Z 6` сразу в файл копии, с `--no-owner --no-acl`:
один код возврата, без промежуточного несжатого файла. Архив имеет права
0600 с момента создания и проверяется `gzip -t`.

После успешного обновления скрипт оставляет пять последних завершённых
пар со своей меткой. Чужие файлы, ручные дампы, символические ссылки и
незавершённые копии он не удаляет. После неудачного обновления копии не
прореживаются. Это копии базы и бинарника перед обновлением, а не полная
резервная копия магазина и не замена регулярному сохранению на другой
носитель.

## Если новая служба не запустилась

Ответ на собственном порту ожидается до 300 секунд. Если новая версия
падает сразу после запуска — systemd трижды перезапустил её или перестал
пытаться, — скрипт не ждёт до конца и возвращает прежний бинарник сразу:
магазин простаивает секунды, а не пять минут.

При ошибке или прерывании скрипт проверяет активность службы. **Если
служба работает без падений, новый бинарник остаётся:** миграции могли
уже примениться, а ответ пока не появился. Установщик сообщает об этом и
завершает работу с ошибкой; проверьте журнал.

Если служба неактивна или падает, скрипт возвращает сохранённый бинарник,
перезапускает службу и проверяет ответ ещё раз. В сообщении будут пути к
прежнему бинарнику и дампу. Если возврат не помог, смотрите журнал:

```sh
systemctl status flycms
journalctl -u flycms -n 50 --no-pager
```

База **автоматически не восстанавливается**. Новая версия могла уже
применить миграции; прежний бинарник может быть несовместим с этой схемой.
Если он не запускается, оставьте магазин остановленным и восстановите
базу по инструкции ниже. Восстановление снимка потеряет изменения,
которые появились в базе после его создания.

## Резервная копия

Для полной ручной копии остановите магазин. Команды ниже выполняются
от root. Для каждого сохранения создаётся отдельная папка в `/var/tmp`:

```sh
umask 077
saved=$(mktemp -d /var/tmp/flycms-backup-XXXX)
systemctl stop flycms
systemd-run --wait --pipe --collect --uid=flycms --gid=flycms \
  --property=WorkingDirectory=/opt/flycms \
  --property=EnvironmentFile=/etc/flycms.env \
  /bin/sh -c 'exec pg_dump -w --no-owner --no-acl -Z 6 --dbname="$FLYCMS_DSN"' \
  >"$saved/database.sql.gz"
```

Проверьте код завершения: при ошибке не продолжайте копирование как
успешное и запустите прежнюю службу. После успешного дампа:

```sh
gzip -t "$saved/database.sql.gz"
cp -p /usr/local/bin/flycms "$saved/flycms"
cp -p /etc/flycms.env /etc/systemd/system/flycms.service "$saved/"
tar -czf "$saved/data.tar.gz" -C /opt/flycms files plugins certs
systemctl start flycms
printf 'Копия: %s\n' "$saved"
```

У магазина версии v0.1.0 папки `/opt/flycms/certs` ещё нет — сертификаты
лежат внутри `files`, и `tar` остановится на `certs`. Уберите `certs` из
команды: папка появится после обновления.

Если в переменных заданы другие папки или используются systemd drop-in
файлы, сохраните и их. Объекты из S3 копируются средствами выбранного
хранилища. Сохраните папку на отдельный носитель с доступом только
владельцу. Внутри есть код установки, ключи и содержимое базы.

## Восстановление базы

Выполняйте от root. Возьмите дамп и бинарник с одинаковой датой и версией.
Скрипт не делает эти действия автоматически. Сначала остановите магазин
и убедитесь, что архив цел:

```sh
systemctl stop flycms
dump=/opt/flycms/backup/20261113T120000Z-v0.1.0.sql.gz
previous=/opt/flycms/backup/20261113T120000Z-v0.1.0.flycms
gzip -t "$dump"
umask 077
restore=$(mktemp -d /var/tmp/flycms-restore-XXXX)
gzip -dc "$dump" >"$restore/database.sql"
```

Продолжайте только после успешной проверки и распаковки. Создайте
**новую пустую базу**, чтобы прежняя осталась доступна для разбора.
Для обычной установки с локальным кластером на стандартном порту:

```sh
restored_db=flycms_restore_$(date -u +%Y%m%d%H%M%S)
runuser -u postgres -- createdb -w -h /run/postgresql -p 5432 -O flycms "$restored_db"
runuser -u flycms -- psql -X -w -v ON_ERROR_STOP=1 \
  --dbname="postgres:///$restored_db?host=/run/postgresql&sslmode=disable" \
  <"$restore/database.sql"
```

Проверьте успешное завершение `psql`, замените в `/etc/flycms.env` только
имя базы в `FLYCMS_DSN` на значение `$restored_db`. При нестандартном
сокете или порте используйте параметры своего кластера.
Затем верните соответствующий бинарник и запустите магазин:

```sh
install -o root -g root -m 755 "$previous" /usr/local/bin/flycms
systemctl restart flycms
systemctl status flycms
journalctl -u flycms -n 50 --no-pager
```

Проверьте витрину, вход владельца, товары и заказы. При восстановлении
полной ручной копии возвращайте также её настройки и данные из
`data.tar.gz`; распаковывайте архив только при остановленной службе,
сохраняя владельцев папок и права 0700 на сертификаты. Изменения файлов
после даты копии сначала сохраните отдельно.
