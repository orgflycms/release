# Установка

```sh
curl -fsSL https://raw.githubusercontent.com/orgflycms/release/main/install.sh | sudo sh
```

## Требования к серверу

- **Система** — Linux с systemd. Postgres установщик ставит сам на Debian 12
  (bookworm), Debian 13 (trixie), Ubuntu 22.04 (jammy) и Ubuntu 24.04
  (noble). Если `psql` на сервере уже есть, список версий системы не
  проверяется.
- **Архитектура** — amd64 или arm64.
- **Postgres 18 или новее.** На сервер без Postgres установщик ставит 18 из
  PGDG. Если Postgres уже стоит и он старше 18, установка останавливается в
  самом начале, ничего не изменив на сервере.
- **Порты** — 80 и 443 свободны и открыты снаружи. Если они заняты своим
  nginx — раздел [«Уже есть nginx на 80 и 443»](#уже-есть-nginx-на-80-и-443).
- Права root, `curl`, доступ к GitHub и, при установке пакетов, к
  репозиториям apt. Docker не нужен.

Версия Postgres проверяется у той базы, с которой будет работать магазин:
у локального сервера на `/run/postgresql:5432`, а если задан свой
`FLYCMS_DSN` — запросом к серверу из него, в том числе удалённому. Сервер
старше 18 — ошибка с найденной и нужной версией. Что делать:

- обновить Postgres до 18 — [update.md](update.md#обновление-postgres);
- поставить магазин на сервер без Postgres — установщик поставит 18 сам;
- указать свою базу на Postgres 18 или новее:

  ```sh
  curl -fsSL https://raw.githubusercontent.com/orgflycms/release/main/install.sh | sudo FLYCMS_HOST=shop.example FLYCMS_DSN='postgres://shop:пароль@db.example:5432/shop' sh
  ```

  `FLYCMS_DSN` из окружения записывается в `/etc/flycms.env` при первой
  установке; роль и базу на таком сервере установщик не создаёт.

Та же проверка стоит при обновлении магазина. Если версию определить не
удалось (сервер не отвечает, нет доступа), установщик из-за версии не
останавливается — о недоступной базе он сообщит проверкой соединения.

## Что делает скрипт

1. определяет тег релиза, скачивает бинарник в `/usr/local/bin/flycms.new`
   и `SHA256SUMS` из этого же релиза, сверяет SHA-256 до первого запуска.
   Проверка не требует исполнения файлов из `/var/tmp`; временный
   бинарник убирается при завершении, в том числе при ошибке;
2. если клиента PostgreSQL нет, ставит PostgreSQL 18 из PGDG; при наличии
   клиента проверяет существующий сервер, не меняя его настройки. Версия
   сервера проверена ещё до первого шага;
3. заводит пользователя службы `flycms` и папки данных. Если при первой
   установке роль или база `flycms` уже существует без `/etc/flycms.env`,
   останавливается, чтобы не подхватить чужие данные;
4. спрашивает адрес (или берёт `FLYCMS_HOST` из окружения), сохраняет
   `/etc/flycms.env` с кодом установки, затем создаёт недостающие роль и
   базу `flycms`. Для стандартной установки нужен локальный PostgreSQL на
   `/run/postgresql:5432` с `peer` для `postgres` и `flycms`. Если создание
   роли или базы прервалось, повторный запуск продолжит с сохранёнными
   настройками и кодом, без ручного удаления созданных объектов;
5. выдаёт роли базы право `CREATEROLE` — при каждом запуске, в том числе
   при обновлении, если у неё его ещё нет и база стандартная: магазин
   заводит им роли плагинов (раздел [«Права роли базы»](#права-роли-базы)).
   У своей базы или если не вышло — предупреждение, установка идёт дальше;
6. кладёт движок в `/usr/local/bin/flycms` и `flycms.service` из тега
   того же релиза, запускает службу и проверяет ответ на её собственном
   порту. Уже стоящий unit-файл, если он отличается, заменяется с
   предупреждением — раздел [«Свои настройки службы»](#свои-настройки-службы).

В конце появится ссылка `https://<адрес>/install?token=<код>`. Откройте
именно её: без кода визард недоступен. Ссылка печатается при каждом
успешном запуске, пока код есть в env-файле; настроенному магазину она не
нужна. Визард спросит название магазина,
контакт, логин и пароль владельца, предложит демо-товары. После создания
владельца визард закрывается. Код хранится в `FLYCMS_INSTALL_TOKEN` в
`/etc/flycms.env`; при обновлении он не меняется. Если в старой установке
кода нет, скрипт его не создаёт: для ненастроенного магазина дальнейшие
действия подскажет движок.

Кириллические домены, в том числе `.рф`, допустимы. Из введённого адреса
для ссылки убираются схема и хвостовые `/`; пробелы и переводы строк
недопустимы. Без терминала используется адрес из `hostname -I`, а если он
не определён — подсказка `адрес-сервера`. Задайте правильный адрес в
`FLYCMS_HOST` в `/etc/flycms.env`, после настройки — в админке.

Для установки без вопросов в терминале:

```sh
curl -fsSL https://raw.githubusercontent.com/orgflycms/release/main/install.sh | sudo FLYCMS_HOST=shop.example sh
```

## Что где

```
/usr/local/bin/flycms            движок
/etc/flycms.env                  настройки и код установки, root:flycms 0640
/etc/systemd/system/flycms.service         unit релиза, заменяется при обновлении
/etc/systemd/system/flycms.service.d/      свои настройки службы, установщик не трогает
/opt/flycms/files/               картинки, пока не задано хранилище S3
/opt/flycms/plugins/             по подпапке на плагин
/opt/flycms/certs/               сертификаты и ключи, flycms:flycms 0700
/opt/flycms/backup/              копии перед обновлением, root:root 0700
```

`/opt/flycms` принадлежит root; служба может писать в `files/`, `plugins/`
и `certs/`, но не в папку резервных копий. Стандартная база — локальный
PostgreSQL, роль `flycms`, вход по сокету без пароля. Для полной копии
магазина нужны база, файлы, плагины, сертификаты и настройки — порядок
описан в [update.md](update.md#резервная-копия).

```sh
systemctl status flycms
journalctl -u flycms -f
systemctl restart flycms     # после правки /etc/flycms.env
```

Временная папка `/var/tmp/flycms-install-XXXX` печатается в начале
установки и остаётся для диагностики с правами 0700. Бинарник из неё не
запускается; автоматический дамп также сразу пишется в папку копий и не
создаёт промежуточного несжатого SQL в `/var/tmp`.

## Домен и https

Движок держит 80 и 443 сам. Право слушать низкие порты даёт systemd;
магазину root не нужен.

Домен берётся из «Адреса магазина» в настройках (Система → Настройки), а
пока он пуст — из `FLYCMS_HOST`. Впишите `https://ваш-домен`, сохраните и
нажмите «Выпустить сертификат» в карточке «Домен и https». Движок проверит
A-запись и получит сертификат у Let's Encrypt — нужны открытые 80 и 443;
продление он берёт на себя. Для IP используется самоподписанный
сертификат: браузер предупредит о нём.

Сертификаты и ключи лежат в `/opt/flycms/certs`, отдельно от картинок.
Сохраняйте эту папку вместе с резервной копией магазина, чтобы не
выпускать сертификаты заново. Сменить домен можно в настройках и повторно
нажать «Выпустить сертификат», без перезапуска.

Перенос сертификатов из старой папки картинок выполняет движок от имени
службы. Установщик создаёт `/opt/flycms/certs` с правами 0700, не копирует
ключи и не добавляет переменные путей сертификатов: по умолчанию движок
выбирает `certs` рядом с папкой файлов. Явно заданные пути в env-файле
сохраняются. При каждом запуске скрипт рекурсивно возвращает владельца
`flycms` папкам `files`, `plugins` и `certs`; резервные копии остаются у root.

## Переменные движка

Живут в `/etc/flycms.env`, читаются службой при старте. Формат для
установщика — отдельная строка `ИМЯ=значение`, при необходимости с
окружающими одинарными или двойными кавычками. Подстановки команд,
переменных и экранирование не используются. Не подключайте этот файл
через `source`: строка подключения содержит `&`.

- `FLYCMS_DSN` — строка подключения к базе. По
  умолчанию `postgres:///flycms?host=/run/postgresql&sslmode=disable`.
  Установщик проверяет `SELECT 1` от пользователя службы с этим DSN;
  допускаются другая роль, пароль, TCP или удалённая база — на Postgres 18
  или новее. Кластер при
  обновлении не перенастраивается; единственное, что установщик меняет у
  стандартной базы, — право `CREATEROLE` роли `flycms`, у другой — только
  предупреждает ([«Права роли базы»](#права-роли-базы));
- `FLYCMS_FILES` — папка картинок (`/opt/flycms/files`);
- `FLYCMS_PLUGINS` — папка плагинов (`/opt/flycms/plugins`);
- `FLYCMS_CERTS` — необязательный явный путь к кэшу сертификатов
  (по умолчанию `/opt/flycms/certs`);
- `FLYCMS_TLS_CERT`, `FLYCMS_TLS_KEY` — необязательные явные пути для
  самоподписанного https (`/opt/flycms/certs/cert.pem` и `key.pem`);
- `FLYCMS_MARKETPLACE` — API маркетплейса (`https://flycms.ru/api/v1`);
- `FLYCMS_HOST` — домен или IP при установке; после сохранения «Адреса
  магазина» в настройках не используется;
- `FLYCMS_INSTALL_TOKEN` — код первого входа в визард;
- `FLYCMS_ADDR`, `FLYCMS_TLS_ADDR` — адреса прослушивания (`:80`, `:443`).
  Пустой `FLYCMS_ADDR` означает `:80`; пустой `FLYCMS_TLS_ADDR` выключает
  собственный https.

Обновление дописывает отсутствующие настройки, сохраняя существующие
значения, в том числе пустой `FLYCMS_TLS_ADDR`.

## Свои настройки службы

`/etc/systemd/system/flycms.service` принадлежит установщику: при
обновлении он заменяется unit-файлом релиза, если отличается от него.
Перед заменой скрипт печатает предупреждение и ждёт 15 секунд — за это
время обновление можно прервать `Ctrl+C`, ничего ещё не изменено. Прежний
файл сохраняется рядом как `flycms.service.prev-<дата и время>`; эти копии
установщик не удаляет.

Свои настройки держите в каталоге переопределений — его установщик не
читает и не меняет:

```sh
systemctl edit flycms
```

Команда создаст `/etc/systemd/system/flycms.service.d/override.conf` и
перечитает настройки; после правки — `systemctl restart flycms`. Туда же
перенесите то, что раньше правили прямо в unit-файле. Настройки из этого
каталога учитывайте при проверке адресов службы.

## Уже есть nginx на 80 и 443

В `/etc/flycms.env` замените строки адресов, не создавая дубликатов:

```ini
FLYCMS_ADDR=127.0.0.1:8080
FLYCMS_TLS_ADDR=
```

После `systemctl restart flycms` настройте `location /` в существующем
HTTPS-блоке `server` магазина в nginx:

```nginx
location / {
    client_max_body_size 256m;

    proxy_pass http://127.0.0.1:8080;
    proxy_set_header Host $host;
    proxy_set_header X-Forwarded-Proto $scheme;
    proxy_set_header X-Forwarded-Host $host;
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
}
```

Без этих заголовков админка может отвечать 403 «Недопустимый источник
запроса», в sitemap и canonical вместо публичного домена может
появиться `127.0.0.1`, а лицензионный ключ не будет принят: он действует,
когда магазин отвечает на домене лицензии, и этот домен движок узнаёт из
`Host` или `X-Forwarded-Host`. Nginx подключается к движку локально по
`127.0.0.1:8080`, поэтому движок принимает от него `X-Forwarded-*`.
Сертификат и внешний https в этом случае держит nginx.

В админке («Система → Настройки») задайте «Адрес магазина» как публичный
https-адрес, например `https://shop.example`.

`client_max_body_size 256m` даёт место для пакетной загрузки изображений
товаров и импорта CSV. Если увеличиваете размер загружаемых изображений
в настройках магазина, увеличьте и лимит nginx с учётом всей отправки.
Проверьте и примените настройки: `nginx -t && systemctl reload nginx`.

На первой установке адреса можно передать сразу:

```sh
curl -fsSL https://raw.githubusercontent.com/orgflycms/release/main/install.sh | sudo FLYCMS_HOST=shop.example FLYCMS_ADDR=127.0.0.1:8080 FLYCMS_TLS_ADDR= sh
```

Проверка установщика обращается к `FLYCMS_ADDR` или `FLYCMS_TLS_ADDR`
и требует, чтобы порт слушал процесс службы `flycms`. Ответ другого
веб-сервера на 80/443 за успешный запуск не принимается. Заголовок `Host`
с адресом магазина в локальную проверку не передаётся. Если 80/443 заняты
другим процессом, установщик предупредит об этом.

## Права роли базы

У каждого плагина своя роль Postgres: так плагин видит только свои таблицы
и те данные магазина, которые вы ему разрешили, а настройки, пароли и
ключи оплаты — никогда. Эти роли заводит сам магазин, и для этого его роли
базы нужно право `CREATEROLE`:

- **стандартная база** (локальный Postgres, `FLYCMS_DSN` по умолчанию) —
  установщик выдаёт право сам, от `postgres`, при установке и каждом
  обновлении; повторный запуск ничего не меняет;
- **другая база** (свой `FLYCMS_DSN`) — установщик её не трогает: если у
  роли права нет, он печатает предупреждение и команду
  `ALTER ROLE <роль> CREATEROLE` для суперпользователя;
- **права нет** — магазин работает, плагинам с доступом к базе она
  закрыта: на странице «Плагины» плашка с той же командой. Плагины, которым
  база не нужна (например, оплаты), работают.

На Postgres 18 `CREATEROLE` позволяет управлять только ролями, которые
роль создала сама: чужие роли сервера ей недоступны. Выдать право вручную:

```sh
su postgres -c "psql -c 'ALTER ROLE flycms CREATEROLE'"
```

Роли плагинов входят паролем по TCP на `127.0.0.1` того же порта. Строка
`host all all 127.0.0.1/32 scram-sha-256` в `pg_hba.conf` у PGDG есть по
умолчанию; если у стандартной базы вход не пройдёт, установщик
предупредит, но `pg_hba.conf` не меняет. Подробнее о правах плагинов —
[plugins.md](plugins.md#права-к-базе).

## Сброс пароля владельца

От root запустите команду от пользователя службы с теми же переменными,
которые читает магазин. Введите новый пароль в стандартный ввод:

```sh
systemd-run --wait --pipe --collect --uid=flycms --gid=flycms \
  --property=WorkingDirectory=/opt/flycms \
  --property=EnvironmentFile=/etc/flycms.env \
  /usr/local/bin/flycms -reset-password
```

Пароль не передавайте аргументом команды. Файл окружения читает systemd,
поэтому кавычки и `&` в DSN не превращаются в команды оболочки.

## Плагины

Готовые — в админке, раздел «Маркетплейс». Свой — папка
`/opt/flycms/plugins/<пространство.имя>/` с Go-файлами и
«Плагины → Перечитать». Подробнее — [plugins.md](plugins.md).

## Удаление

Сначала сохраните полную резервную копию: команды ниже удаляют магазин
и его базу. PostgreSQL остаётся — он может быть нужен другим приложениям.

```sh
systemctl disable --now flycms
rm -f /etc/systemd/system/flycms.service /etc/flycms.env /usr/local/bin/flycms
systemctl daemon-reload
su postgres -c 'dropdb flycms; dropuser flycms'
rm -rf /opt/flycms
userdel flycms
```

Копии `flycms.service.prev-*` и каталог `flycms.service.d` в
`/etc/systemd/system`, если они есть, удалите отдельно.

Если при восстановлении меняли имя базы, удаляйте только проверенную базу
магазина, а не базу с именем из примера.
